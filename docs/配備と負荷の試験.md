# 配備と負荷の試験

共有メーターの API（`src/server/`）の、配備物の作り方・配備の手順の案・起動の確かめ方・戻し方・負荷の試験の手順をまとめます。

> **この文書は手順の案です。配備は、統括の承認を受けてから、タキシードサムが行います。** この文書の手順を、承認なしに実行しません（本番の Azure に触れるコマンドは、リポジトリの `.claude/settings.json` でも拒否しています）。
> Public のリポジトリなので、**API の URL・Azure のリソースの実際の名前・合言葉は、この文書にもコードにも書きません。** 例の中の `<...>` は、実行する人が入れ替えます。

## 1. 配備物を作る

```bash
npm ci
npm run verify     # lint → 整形 → 秘密の検査 → 型 → テスト → ビルド。エラー 0 を確かめてから作る
npm run package    # artifacts/ に zip ができる
```

`npm run package` は、次を行います。

- `src/server/index.ts` を、esbuild で 1 ファイル（`dist/server/server.mjs`）に束ねる。外部の依存が束ねから漏れていたら、ここで失敗する。
- `server.mjs` と `package.json`（`{"type":"module"}` だけ）を、zip にする。`node_modules` は要らない。
- 出力: `artifacts/oshiyobu-api-<core の版>-<コミット ID>.zip`。大きさと SHA-256 を表示する。未コミットの変更があると、名前の終わりに `-dirty` が付く。**配備するのは、コミットした状態から作った zip だけ**にしてください（`-dirty` の zip は配備しない）。

zip は、同じ入力から毎回同じバイト列になります（更新日時を固定しているため）。前の版の zip は、`artifacts/` に残します（Git には入れません）。切り戻しに使います。

確かめるときは、次のコマンドを使います（どちらも読み取りだけです）。

```bash
unzip -l artifacts/<zip の名前>    # server.mjs と package.json の 2 つだけ
unzip -t artifacts/<zip の名前>    # 壊れていないこと
```

## 2. 環境変数

Azure の App Service の「アプリ設定」に、同じ名前で入れます。一覧は `.env.example` にもあります（値は空）。

| 名前                             | 意味                                                                                               | 秘密     | 設定する人         |
| -------------------------------- | -------------------------------------------------------------------------------------------------- | -------- | ------------------ |
| `PRESENTER_PASSPHRASE`           | 発表者の合言葉。12 文字以上。未設定・12 文字未満だと、reset は 503 で無効になる                    | **秘密** | 統括               |
| `CORS_ORIGINS`                   | 画面（frontend）の origin。カンマ区切り・完全一致。末尾の `/` は付けない。ワイルドカードは使えない | 公開     | タキシードサム     |
| `DATA_DIR`                       | 保存先のフォルダ。Azure は `/home/data`。起動時に作る                                              | 公開     | タキシードサム     |
| `NODE_ENV`                       | `production`。未設定のときだけ、開発の画面（`http://localhost:5173`）も許す                        | 公開     | タキシードサム     |
| `PORT`                           | 待ち受けの番号。App Service が渡す。無ければ 8787                                                  | 公開     | App Service が渡す |
| `SCM_DO_BUILD_DURING_DEPLOYMENT` | `false`（Oryx でビルドしない。配備物は、束ね済みの 1 ファイル）                                    | 公開     | タキシードサム     |

- 起動に失敗して、ポートが合っていないと分かったときは、アプリ設定の `WEBSITES_PORT` で合わせます（Linux の Node で `PORT` が渡される想定ですが、実際の配備で確かめる項目です）。
- 値が間違っていても、起動はします。使えない値は既定値になり、起動ログに警告（`config_warning`）が出ます（値は出ません）。`CORS_ORIGINS` の書き間違いは、ブラウザからは見えにくいので、起動ログの警告を見てください。
- 合言葉の値は、ログにも、応答にも出ません。

## 3. 配備の手順（案）

設計 D-23 のとおり、既存の B1 プラン（`asp-guapp-nonooktk`）に相乗りする Linux の Web アプリ（`NODE|22-lts`）です。**インスタンスは 1 つ**にします（スケールアウトすると、人数の状態が割れます）。Always On・HTTPS のみ・FTPS 無効にします。

```bash
# 配備（zip の配備。<...> は入れ替える）
az webapp deploy --resource-group <リソースグループ> --name <Web アプリの名前> \
  --src-path artifacts/<zip の名前> --type zip

# 初めての配備のときだけ（アプリ設定。値は統括が入れる。PRESENTER_PASSPHRASE はここに書かない）
az webapp config appsettings set --resource-group <リソースグループ> --name <Web アプリの名前> \
  --settings NODE_ENV=production DATA_DIR=/home/data SCM_DO_BUILD_DURING_DEPLOYMENT=false CORS_ORIGINS=<画面の origin>
az webapp config set --resource-group <リソースグループ> --name <Web アプリの名前> \
  --startup-file "node server.mjs" --always-on true --ftps-state Disabled
az webapp update --resource-group <リソースグループ> --name <Web アプリの名前> --https-only true
```

- 手元からの配備は、統括の承認があった範囲だけです。承認の前に、実行しません。
- 負荷の試験で基準を満たせなかったときの、専用プランへの付け替えは、設計 D-43 にあります。

## 4. 起動の確かめ方

配備したあと、次の順に確かめます（`<API の URL>` は入れ替える）。

```bash
# 1. 生存と、core の版
curl -s <API の URL>/healthz
#   → {"ok":true,"coreVersion":"<zip の名前に入っている core の版>"} になること

# 2. 公演 1 件の取得（terao:KGS-001 は、発表に使わない公演）
curl -s <API の URL>/api/v1/performances/terao:KGS-001/meter
#   → {"performanceId":"terao:KGS-001","joined":<件数>,"resetAt":...} になること

# 3. 書き込みを含む確認は、テスト用の端末の番号で。聞き手の数を書き換えない時間帯に行う
curl -s -X POST -H 'content-type: text/plain' \
  --data '{"deviceId":"<16〜64 文字の英数字・_・->"}' <API の URL>/api/v1/performances/terao:KGS-001/joins
#   → counted: true。同じ端末の番号でもう一度送ると counted: false
```

- 応答のヘッダーに、`Server-Timing: app;dur=…` があること。
- 起動ログに、`server_started`（`port`・`persistence: true`・`coreVersion`）があること。`persistence_disabled` が出ていたら、`DATA_DIR` に書けていません（人数は、再起動で消えます）。
- ログの見方: 1 行 1 件の JSON です。`event` が `join`・`reset`・`reset_unauthorized`・`config_warning`・`persist_failed` などです。IP・端末の番号・本文・合言葉は、出ません。

## 5. 戻し方（切り戻し）

- 前の版の zip（`artifacts/` に残したもの）を、手順 3 の `az webapp deploy` で、もう一度配備します。アプリ設定は変えません。
- 保存ファイル（`/home/data/meter.json`）は、配備では消えません。形（`v: 1`）が同じなら、前の版でもそのまま読めます。
- 人数を空にしたいときは、`/presenter/` の reset（合言葉）を使います。

## 6. 手元でサーバーを動かす

```bash
npm run build
PORT=8787 DATA_DIR=./data NODE_ENV=production CORS_ORIGINS=<画面の origin> npm start
# 合言葉を使う試験のときは、PRESENTER_PASSPHRASE も、環境変数で渡す（値はコマンドの履歴に残さない工夫を。このファイルには書かない）
```

`.env` を使うときは、`.env.example` をコピーして値を入れ、`node --env-file=.env dist/server/server.mjs` で読み込めます（`.env` はコミットしません）。

## 7. 負荷の試験

設計 D-42 の基準です。k6 は、**コーディネーター側の Mac** で実行します。本番の B1 に当てる試験は、統括の承認と、実行の直前の一言のあとに行います。

### 合格の線

| 項目                                                  | 基準                                                      |
| ----------------------------------------------------- | --------------------------------------------------------- |
| 応答（全体・取得だけ・申し込みだけ）                  | p95 が 500 ms 未満                                        |
| サーバーの中の処理（応答の `Server-Timing`）          | p95 が 50 ms 未満                                         |
| エラー（通信の失敗・5xx・想定外の 4xx。409 は想定内） | 1% 未満                                                   |
| 429                                                   | **0 件**（同じ接続元から 100 台ぶん使っても、弾かれない） |
| 出し切れなかった要求                                  | 0 件                                                      |
| 申し込み後の `joined`                                 | 申し込み件数ちょうど増える（`counted: true` も同じ件数）  |

### k6 での実行

```bash
# k6 の入れ方（Mac）: brew install k6
k6 run -e BASE=<API の URL> -e CLIENTS=100 loadtest/n22.js   # 合格の線。100 台を 2 回
k6 run -e BASE=<API の URL> -e CLIENTS=150 loadtest/n22.js   # 余裕の確認。1 回
```

- 取得は毎秒（台数 ÷ 2）回、申し込みは開始 30 秒後から 10 秒間に（台数 ÷ 2）件。100 秒続けます。1 つの IP から出します。
- 公演は、既定で発表に使わない `terao:KGS-001` です（`-e PID=` で変えられますが、発表に使う公演には当てません）。
- 結果は、合否・p95・`server_ms` の p95・エラー・429 の 1 行で出ます。1 つでも閾値を外れると、終了コードが 0 でなくなります。
  詳しい数字（各指標の最小・中央値・最大など）が要るときは、`--summary-export=summary.json` を付けます。
- 実行の前後に `GET /healthz` が 200 であること、実行の後に `joined` が申し込み件数ちょうど増えていることも、自動で確かめます。
- 試験の件数は、reset するまで残ります。全体の上限（1,500 件）に近づく前（合計が 1,000 件を超えたとき）に、統括が reset します。発表の 30 分前の reset が、試験の件数もまとめて消します。
- 試験の間、タキシードサムが、プランの CPU と、同じプランの他のアプリの様子を記録します。CPU の最大が 70% を超えたときは、合否とは別に統括へ伝えます。

### k6 が無いとき（Node の代わりの台本）

手元のサーバー（`127.0.0.1`）で、台本の数字と閾値を確かめる道具です。同じ PC でサーバーと台本が動くので、本番の通信の遅れ・接続数は再現しません（本番の試験は k6 で行います）。

```bash
npm run build
PORT=8787 DATA_DIR=./data NODE_ENV=production npm start      # 別のターミナルで
npm run loadtest -- --base http://127.0.0.1:8787 --clients 100   # 100 台（約 100 秒）
npm run loadtest -- --base http://127.0.0.1:8787 --clients 150   # 150 台
```

`--duration`・`--join-start`・`--join-window`・`--joins` で、秒数と申し込み件数を変えられます（例: `--clients 100 --joins 100 --join-start 5 --join-window 10 --duration 30` は、100 台が 10 秒のあいだに 1 回ずつ申し込む試験）。合格しなかったときは、終了コード 1 で、理由を出します。
